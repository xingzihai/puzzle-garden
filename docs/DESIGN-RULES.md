# 设计规则：硬限制与创作自由

> 状态：**生效中**，2026-10-22。
> 来源：项目维护者对硬限制与创作自由边界的明确要求。
> 适用范围：交互层、构建层、验收层，以及后续所有 agent 设计。

## 0. 一句话

**硬限制只用于安全、不可逆和技术完整性；不用于创作。让 agent 把活干好，靠好的提示词、工具和示例，不靠事后法医式的硬门。**

## 1. 可以做硬限制的地方

只有以下情况允许阻塞交付或 accept：

1. **安全**：密钥/隐私泄露、沙箱逃逸、危险操作；
2. **不可逆/技术完整性**：空交付、无存档、存档损坏、费用/时间/轮数超限；
3. **用户明确确认的合同底线**：例如外轮廓、入口方向——仅当用户把它明确标为 must；
4. **数据真实性**：不能把 `unverified` 写成 `met`，不能伪造证据。

除此之外，一律不做硬限制。

## 2. 不允许做硬限制的地方

以下属于创作表达，**不得**用硬门、`not-met` 或 accept 阻塞来限制：

- 材质、颜色、纹理、明暗、方块选择；
- 建筑形式、屋面做法、立面节奏、装饰细节；
- 家具样式、尺寸微差、摆放的审美判断；
- 空间氛围、叙事、风格；
- 任何“90% 必须是某种材料”“必须是某种形状”的规则；
- 任何 as-built 事后分类器推断出的“创作意图”，都不能反过来判死作品。

这些最多作为 **review 里的观察/建议**，由用户判断。

## 3. 验收的正确形态

系统应该报告：

- 实际建成了什么；
- 和设计/需求相比，哪里不同；
- 哪些项有证据、哪些没有（`unverified`）；
- 哪些是真正的安全问题/技术问题。

然后由用户看房子、看报告，做最终 **accept / reject**。系统不替用户判“好不好看”，也不把“材质比例不够”升级成硬失败。

## 4. 正确做法靠引导，不靠事后法医

优先顺序：

1. 好的施工手册 / playbook；
2. 好用的高层 API，让正确做法成为最省事的路；
3. 好的示例和默认值；
4. 局部、轻量的观察工具（probe / check）；
5. 只有在第 1–4 都做不到时，才考虑确定性检查。

不要为了抓 agent 的低层写法，去建一个复杂的 as-built 分类器，再为它的误报不断加特判。

## 5. 如果检查经常误判

- 降级为 advisory，或删除；
- 不要继续加“形状白名单”“材质比例”“否定词表”之类的补丁；
- 不用“为了保住覆盖数字”而保留假通过或假失败。

## 6. 与旧策略的关系

本规则**取代**之前所有“创作类硬门”的实现，包括但不限于：

- 墙体材质 ≥90% 硬门；
- 隔断/材质角色/家具形状的 `not-met` 硬判定；
- 用 as-built 分类器反推创作意图并阻塞 accept。

这些检查可以保留为 review 的观察信息，但不得阻塞交付或 accept。

## 7. 判断标准

遇到一个新检查，先问：

1. 这是安全/不可逆/技术完整性问题吗？
2. 这是用户明确确认的合同底线吗？
3. 如果误判，会不会伤害创作？

如果 1 和 2 都是“否”，它就不该是硬限制。
