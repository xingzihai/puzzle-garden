## 0. 结论摘要

1. **当前项目已经有一条可用的“构建 agent”链路，但还没有“用户交互 agent”。** `runRun` 一次只接收一份题面，由模型写代码、检查、看图、提交；用户没有参与澄清、方案确认和修改的入口。`write_design` 是构建过程内部的设计笔记，不是用户确认过的方案。
2. **当前质量瓶颈已经从“能不能搭起来”转向“上游设计是否具体、可执行、可核对”。** 历史实验表明：带有坐标骨架的执行版题面能降低失败率与成本，但没有自动抬高审美上限；让构建 agent 自己写更长的设计文档也没有整体提升。真正缺的是构建之前的方案设计，而不是更长的提示词。
3. **建议新建 `@pg/interaction`（第 4 层）作为用户交互层。** 它负责语义理解、澄清、建筑专业分析、方案设计、版本管理、提示词 / 构建简报生成、结果评审与定向修改；构建仍复用现有 `@pg/agent` 与沙箱，不另做第二套构建循环。
4. **首版聚焦 1–3 层、占地约 8–30 m、5k–30k 实心方块的中小型建筑。** 默认范围是“外观 + 入口 + 场地 + 完整室内（主要空间、家具、楼层、固定家具）”；巨构、城市级场景、大型教堂 / 高塔降为回归能力，不作为开发主线。
5. **实施顺序应该是“先方案，后提示词，再构建，再反馈”。** 先把用户需求变成可核对、可视化的 `DesignScheme`，再由同一个方案编译出构建简报；构建结果回到同一方案做评审和修改。

### 0.1 Owner 补充（2026-10-19）

这次补充把产品方向进一步钉死：

1. **用户交互 agent 在构建 agent 之前。** 用户不再直接提供题面 / 提示词；交互 agent 与用户交流、询问关键点，并以专业建筑设计师的身份完成方案与实现细节。构建 agent 只负责按设计报告施工。
2. **设计报告是唯一交接物。** 交互 agent 产出高质量的详细设计报告（含需求、场地、平面、标高、结构、外观、室内、家具、材料、细部、验收），构建 agent 按现有方法执行，不再自行重做方案。
3. **室内与外观同等重要。** 室内空间、家具、楼层、门窗、固定家具、灯具、铺装与细部都必须有，且要高质量；不能只做“外观 + 空壳”。
4. **方块与渲染保真度是前置条件。** 方块注册表和渲染器需要优化，尤其是：
   - 六面材质不同的方块（如原木、木柱、竖纹方块）；
   - 非正方体方块（楼梯、台阶、花盆、门、活板门、地毯、压力板等）；
   - 有方向的方块（门、活板门、栅栏门、按钮、告示牌、楼梯等）。
     当前渲染器把大量这类方块统一画成 8×8×8 小方块，必须优先修正，否则“精致室内”在截图里无法成立。
5. **子代理并行开发。** 主代理承担“软件公司”角色：定规格、拆任务、派子代理、验收和集成；具体实现交给子代理，子代理可以继续派次级子代理。每一步操作都要向 owner 报告目的与结果。

## 1. 项目现状

### 1.1 现有端到端链路

```text
题面 markdown
  → @pg/agent/runner（单次 run、追加式历史）
  → LLM tool calls（write_code / edit_code / check_code / view_building / submit …）
  → @pg/sandbox（bwrap + 类型预检）
  → @pg/geometry（World API）或 @pg/modeling（ModelDocument）
  → @pg/analysis（悬空、夹层、可达、屋面、对称等）
  → @pg/render（Chrome + three 截图）
  → 事实行 + 图片回喂
  → submit / 交付
```

这条链路是稳定的工程基础：沙箱、类型预检、事件记录、计费、护栏、渲染、测量、回放都是现成的。当前 `packages/agent` 约有 8k 行非测试代码，`geometry` / `modeling` / `design` / `analysis` / `render` 也都有独立职责与测试。

### 1.2 已有可复用能力

| 能力                                 | 位置                                                 | 对交互层的价值                                  |
| ------------------------------------ | ---------------------------------------------------- | ----------------------------------------------- |
| LLM 客户端、SSE、计费、mock / replay | `packages/llm`                                       | 交互会话直接复用，不新建模型客户端              |
| run 目录、事件流、Blob、请求编码     | `packages/store`                                     | 会话记录可仿照 run store；构建 run 继续独立保存 |
| 体素构件 API                         | `packages/geometry` + `world.d.ts`                   | 设计可行性、坐标骨架、能力卡片的依据            |
| 参数化建模                           | `packages/modeling`                                  | 草模、自由曲面、设计预览的候选表示              |
| 分析测量                             | `packages/analysis`                                  | 可达、悬空、夹层、屋面、对称等客观事实          |
| Blueprint / 净空 / 路线 / 版本差异   | `packages/design`                                    | 方案预览、净空与通行检查、版本对比的基础        |

| 基准题与人工夹具                     | `assets/v02/benchmark`、`packages/geometry/fixtures` | 小体量试点题目与回归样本的来源                  |

### 1.3 关键缺口

| 缺口                       | 现状                                                            | 后果                                                       |
| -------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| **没有交互入口**           | CLI 只接受题面文件；`runRun` 一次 run 一条 user 消息            | 用户无法澄清、确认方案或在中途改变主意                     |
| **设计方案不是一等公民**   | `write_design` 是构建内部工具；`@pg/design` 主要是查看器样例    | 用户确认的是一套，构建层可能另做一套；无法保证“按方案施工” |
| **语义理解未结构化**       | 题面由人预先写好；没有需求抽取、歧义 / 矛盾检测                 | 含糊需求被直接丢给构建层，错误在后期才暴露                 |
| **提示词是静态拼接**       | `system.ts` + 题面；没有编译器 / 检查器                         | 方案信息容易遗漏、重复、互相矛盾；无法按建筑类型选做法     |
| **没有结果回到方案的闭环** | 只能新 run + `--seed-code` + feedback                           | 分不清“方案错了”“施工错了”“用户改主意了”                   |
| **小体量支持不是主线**     | 基准含教堂 / 高塔；`craft` 提示偏哥特巨构；构建提示默认不做内饰 | 容易把“精致小屋”做成缩小版巨构或空壳                       |
| **人眼尺度评审不足**       | 只有正交立面 / 俯视 / 轴测；没有入口、室内、细部视角            | 小体量最关键的檐口、窗框、门槛、家具看不出来               |

### 1.4 历史证据（为什么要改顺序）

- **执行版题面有效，但不是上限。** 历史“提示词质量实验”把同一道教堂题改写成带坐标骨架、建造顺序、细部表和自查清单的执行版；构建层更稳、更便宜、失败更少，但对最好的原题稿只是一胜一负一平。结论是：有用的是“可执行、已验证的坐标骨架”，不是更长的描述。
- **让构建 agent 写更长的设计文档没有整体提升。** 两层实验（骨架 / 细化，各写设计文档）文档确实变长，但条款没有整体变好；方差仍然主导。
- **草模机制没有被自发采用。** 草模接入构建层的对照实验里，A / B 两组在未强制时都零采用；这说明不能把“提供工具”当成“产品流程会使用它”。交互层应该直接调用设计 / 草模能力，而不是指望构建 agent 自己想起来。
- **评审方法仍受位置偏好影响。** 历史盲比多次出现“全判右”，方法需要继续校准；小体量评审应该用随机左右、双判、以及更具体的 rubric。
- **会话独立、不做跨会话记忆。** 既有决策明确每个需求会话相互独立；上一版方案通过显式输入传递，不做自动长期记忆。交互层也遵守这条边界。

### 1.5 为什么转向中小型精致建筑

- **质量可感知。** 小体量的比例、入口、檐口、窗框、材质、家具和光线更容易被人眼直接判断；“精致”有明确的落点，而不是靠体量和尖塔数量。
- **成本与迭代速度更合适。** 5k–30k 方块的建筑可以在更少轮次、更低预算内完成多次方案—构建—修改循环。
- **交互层能真正发挥作用。** 小建筑的功能、场地、动线、结构和外观可以被完整设计；巨构更容易退化成“堆体量 + 堆装饰”。
- **现有提示有巨构偏差。** `packages/agent/src/prompt/craft.ts` 的形态提示大量面向塔、尖顶、飞扶壁、小尖塔（如“天际线尖端 30 个以上”“高度取上沿、宽度取下沿”）。这些对哥特有参考价值，但不适合茶亭、住宅、工作室、小书店。需要独立的 `craft-small` 提示变体。
- **当前基准仍以“能不能做到”组织。** 题面里教堂 40k、塔楼 20k、院落 30k 仍在中型范围，但开发注意力应优先给更小、更日常、更可反复评审的类型。

## 2. 目标与边界

### 2.1 首版产品目标

用户用自然语言提出一个小型建筑需求，交互 agent 能在少量关键提问后，主动完成一套带尺寸、功能、动线、结构、外观和场地的方案；用户通过图与简短说明确认或修改；确认后的方案被编译成高质量构建简报，交给现有构建 agent；构建结果回到同一方案做评审；用户可以用自然语言提出一次定向修改。

一句话：

> **把“用户想要什么”变成“建筑上成立、构建上可执行、结果可核对”的方案，再交给构建层。**

### 2.2 首版范围

| 维度     | 首版建议                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------- |
| 建筑类型 | 茶亭 / 咖啡亭、村居 / 山居、街角工作室 / 小店、小型院落、社区图书室 / 小展厅、山间驿站                   |
| 规模     | 1–3 层；占地约 8–30 m；最高点 ≤ 15 m；5k–30k 实心方块；主要空间 1–8 个                                   |
| 交付范围 | 外观 + 入口 + 紧邻场地 + **室内**；主要室内空间、家具、楼层、固定家具与细部为必需，不能只做空壳          |
| 设计深度 | 带尺寸的平面、标高、主要剖面、门窗、楼梯、屋面、材质、立面节奏、家具、灯具、关键细部                     |
| 用户输入 | 一句话到一段话皆可；允许模糊、矛盾、改主意；允许授权 agent 自主设计                                      |
| 成功标准 | 用户 10 分钟内能看懂方案并确认；构建结果不偏离主要布局；室内与外观同等质量；一次定向修改能保留未点名区域 |
| 运行边界 | 先离线 / mock；真实模型运行按既有规则单独授权；不做跨会话记忆                                            |

### 2.3 非目标

- 不做大教堂、纪念性巨构、城市级街坊、大型基础设施。
- 不替代施工图、结构计算或建筑规范审查；专业分析是设计辅助与可核对的事实，不是执业盖章。
- 不做参考图复刻、自动导出可玩 MC 世界（可作为后续能力）。
- 不做跨会话长期记忆、多模型对照、任意工具 / 联网。
- 不重写现有构建循环、沙箱、渲染或分析；交互层只做上游编排与方案。

## 3. 设计原则

1. **单一方案源。** 需求、方案、构建简报、结果评审都从同一份 `DesignScheme` 派生；不维护“用户版”和“施工版”两套事实。
2. **设计先行，少问关键问题。** 优先给出有理由的方案；只问会改变布局、功能、体量、风格或可行性的问题。已有答案不重复问；不要求用户逐格设计。
3. **可执行 > 更长。** 方案要落到坐标、尺寸、标高、洞口、梯段、材料与数量；一句漂亮描述不能替代可执行的表格。
4. **确定性检查 + 视觉评审分开。** 面积、净空、可达、跨度、预算等用代码算；比例、氛围、精致度用看图评审。两者都在报告里，但不混成一个“通过”。
5. **能力边界前置。** 交互层必须知道当前 World API、渲染、分析能做什么；不支持的承诺要在方案阶段说清楚，不能到构建失败才暴露。
6. **小体量、真实尺度、克制。** 不靠放大体量、堆尖塔或堆装饰制造“精致”；优先比例、开间、檐口、材质层次、门槛与家具。
7. **用户拥有偏好，agent 拥有设计。** 用户决定用途、重要取舍和审美偏好；agent 负责计算、解决空间矛盾、提出方案与后果。
8. **会话独立、版本显式。** 每次会话独立；方案有版本、决策有来源、修改有影响说明；不在讨论中悄悄改掉正在构建的版本。

## 4. 目标架构

### 4.1 分层

```mermaid
flowchart TB
  U[用户] --> CLI[交互 CLI / 后续 Web]
  CLI --> I[@pg/interaction<br/>会话 / 语义 / 设计 / 简报 / 评审]
  I --> D[@pg/design<br/>Blueprint / 净空 / 路线 / 差异]
  I --> K[知识包 / 能力卡]
  I --> A[@pg/agent<br/>现有构建 runner]
  A --> S[@pg/sandbox]
  A --> G[@pg/geometry]
  A --> M[@pg/modeling]
  A --> AN[@pg/analysis]
  A --> R[@pg/render]
  A --> ST[@pg/store]
  I --> ST
  I --> L[@pg/llm]
  CLI --> W[@pg/web<br/>查看器]
  W --> D
  W --> M
```

层级约束：

- `@pg/interaction` 放第 4 层，可以依赖 `@pg/agent`、`@pg/design`（均第 3 层）及更低层。
- **不能**依赖 `@pg/web`（第 5 层）。需要渲染方案预览时，由 `tools/` 组装层注入渲染函数，或者只产出 `Blueprint` / `ModelDocument` 数据，由 web 查看。
- `@pg/web` 保持轻量，不把 `agent` / `sandbox` 拖进浏览器服务；会话数据通过文件或 tools 层提供。
- 新包要登记到 `eslint.config.js` 的 `PACKAGES`、`tsconfig.json`、`tools/check-tests.ts` 与依赖检查中。

### 4.2 `@pg/interaction` 模块

| 模块                 | 职责                                                       | 备注                                  |
| -------------------- | ---------------------------------------------------------- | ------------------------------------- |
| `session.ts`         | 会话状态机、阶段推进、预算 / 取消 / 恢复                   | 不做构建循环                          |
| `store.ts`           | `.work/sessions/<id>/` 事件、Blob、方案版本                | 仿照 run store，但使用独立事件 schema |
| `requirements.ts`    | 需求抽取、来源标注、歧义 / 矛盾 / 缺失检测                 | 结构化输出 + 确定性校验               |
| `clarify.ts`         | 提问策略、问题排序、默认建议                               | 只问高影响项                          |
| `design/scheme.ts`   | `DesignScheme` schema、版本、决策记录                      | 单一方案源                            |
| `design/analyze.ts`  | 场地、功能、面积、动线、结构、环境分析                     | 纯函数优先                            |
| `design/checks.ts`   | 小建筑规则检查（净空、门宽、梯段、跨度、预算等）           | 复用 / 扩展 `@pg/design`              |
| `design/preview.ts`  | 方案 → `Blueprint` / `ModelDocument` / 平面图 / 剖面图     | 渲染由 tools 注入                     |
| `brief/compile.ts`   | `DesignScheme` → `BuildBrief` + `BuildSpec` + `gates.json` | 核心产物                              |
| `brief/lint.ts`      | 需求覆盖、维度一致、能力、预算、禁项检查                   | 构建前必须通过                        |
| `brief/recipes.ts`   | 小建筑细部做法库（檐口、窗框、门槛、栏杆、屋脊等）         | 可版本化                              |
| `review/compare.ts`  | 交付结果 vs `BuildSpec` 的客观对比                         | 坐标 / 数量 / 路线 / 预算             |
| `review/critique.ts` | 看图评审、缺陷分类、修改建议                               | 设计错 / 施工错 / 偏好变              |
| `review/revise.ts`   | 反馈 → 方案更新或定向修改简报                              | 保留未点名区域                        |
| `knowledge/`         | 类型学、风格、功能、细部、常见缺陷                         | 产品知识，不是会话记忆                |
| `cli.ts`             | 交互式命令行入口                                           | 首版入口；Web 后续                    |

### 4.3 会话存储

建议：

```text
.work/sessions/<sessionId>/
  events.jsonl          # session.start / user.message / assistant.message / requirements.version /
                        # design.version / decision / build.start / build.result / review / session.end
  blobs/                # 方案 JSON、图片、简报、评审报告
  designs/              # 可读的方案版本（Markdown / JSON / 预览图）
  builds.json           # session 关联的 build runId 与交付 hash（也可写进 events）
```

- 不把会话事件塞进现有 `RunLimits` / `StopReason` / `events.ts` 的构建事件 schema；两者生命周期不同。
- 复用现有 run store 的路径安全、Blob、单行上限、密钥 / `data:image` 扫描经验。
- 每个构建 run 仍是独立的 `.work/runs/<runId>/`，在 `session` 事件里记录 `runId`、设计版本、交付 hash。
- 会话默认本地保存，`.work/` 不入库；真实用户隐私不进入提示词之外的上传。

## 5. 核心数据模型

### 5.1 `RequirementGraph`

语义理解的结果不是一段摘要，而是可追溯的需求图。

| 字段             | 内容                                                             |
| ---------------- | ---------------------------------------------------------------- |
| `requirements[]` | 归一化需求、用户原话、来源、优先级、状态、影响面                 |
| `spaces[]`       | 功能空间、数量、面积、人数、层、相邻关系、采光 / 隐私 / 噪声要求 |
| `site`           | 场地尺寸、朝向、坡度、入口、退界、周边、室外区域                 |
| `constraints[]`  | 尺寸、层数、预算、材料、禁止项、法规 / 可访问性                  |
| `preferences[]`  | 风格、氛围、材质、颜色、参考感受                                 |
| `ambiguities[]`  | 歧义、可选解释、影响、建议默认值、状态                           |
| `conflicts[]`    | 互相矛盾的需求、涉及条目、可选取舍                               |
| `missing[]`      | 必须由用户决定但尚未决定的事项                                   |
| `capabilities[]` | 当前实现不支持或需替代方案的事项                                 |
| `decisions[]`    | 用户确认、代理建议、默认值、拒绝项                               |

单条需求建议：

```json
{
  "id": "req-014",
  "text": "入口要能直接看到院子里的树",
  "quote": "从门口一进来就能看到那棵树",
  "source": "user",
  "kind": "preference",
  "priority": "should",
  "status": "confirmed",
  "confidence": 0.92,
  "affects": ["site", "plan", "facade", "interior"],
  "evidence": "用户原话第 3 段"
}
```

规则：

- 用户原话、代理推断、默认建议、用户确认必须可区分。
- 代理拟定的尺寸不能自动升级为用户硬要求；只能标为 `proposed` / `assumed`。
- 任何 `must` 若在方案中无法满足，必须转成 `conflict` 或 `capabilities`，不能静默删除。
- 提问数量按影响排序；一次最多 1–3 个高影响问题，简单需求允许零提问直接给方案。

### 5.2 `DesignScheme`

建议以“方案信封 + 几何快照”的方式组织：

| 部分            | 内容                                                                      |
| --------------- | ------------------------------------------------------------------------- |
| `meta`          | id、revision、标题、一句话概念、状态、来源需求版本                        |
| `site`          | 场地边界、朝向、入口、室外分区、铺装、景观、退界                          |
| `levels[]`      | 楼层 id、名称、标高、层高、面积                                           |
| `spaces[]`      | 空间 id、名称、用途、层、bounds、面积、人数、连接                         |
| `elements[]`    | 墙、楼板、屋面、楼梯、栏杆、家具、景观等实体；含厚度 / 材料 / host / 开口 |
| `openings[]`    | 门、窗、洞：host、位置、宽 / 高 / 窗台 / 过梁、填充、框                   |
| `circulation[]` | 入口序列、主要路线、楼梯 / 坡道、关键站立点、无障碍要求                   |
| `structure`     | 结构体系、柱网 / 墙承重、跨度、楼板厚度、悬挑限制                         |
| `roof`          | 形式、坡度、檐口、屋脊、排水、材料、天窗 / 烟囱                           |
| `facades[]`     | 每个立面的基座 / 中段 / 顶部、开间、窗墙比、框、腰线、细部                |
| `materials[]`   | 部位 → 方块 / 明度 / 质感 / 使用规则                                      |
| `details[]`     | 檐口、窗框、门槛、栏杆、屋脊、雨水、长凳、书架等做法与数量                |
| `interiors[]`   | 主要室内空间、家具区、固定家具、采光 / 视线（若在范围）                   |
| `decisions[]`   | 方案决策、备选、理由、用户确认状态                                        |
| `open[]`        | 未决问题、构建阶段可自由发挥的范围                                        |

设计表达建议：

- 用户看的是 **方案摘要 + 平面 / 剖面 / 关键立面 + 3D 草模 / 轴测图**；不需要读坐标表。
- 构建层看的是同一份方案的结构化数据 + 构建简报；两者不各自维护。
- 预览可以是 `Blueprint`（语义、可检查）或 `ModelDocument`（自由形体、可视）；首版优先 `Blueprint` + 一个简单体量，不追求精细渲染。

### 5.3 `BuildBrief` 与 `BuildSpec`

一份确认后的方案编译出：

| 产物               | 用途                                                                                |
| ------------------ | ----------------------------------------------------------------------------------- |
| `design.md`        | 用户确认的方案全文，构建层的唯一设计依据                                            |
| `build-task.md`    | 喂给构建 agent 的四节题面（需求 / 禁项 / 场地尺寸与建造要求 / 验收与自由范围）      |
| `build-spec.json`  | 机器可读的约束：bounds、levels、spaces、openings、routes、counts、budget、forbidden |
| `gates.json`       | 现有 `--gates` 能表达的门槛（结构跨度、可达、悬空来源等）                           |
| `reference/*.png`  | 方案预览、平面 / 剖面 / 关键视角                                                    |
| `prompt-meta.json` | 方案版本、提示词版本、能力卡版本、生成时间                                          |

`BuildSpec` 不是另一套方案，只是同一方案的机器视图；任何字段变化都必须回写 `DesignScheme`。

### 5.4 `ReviewReport`

| 部分                           | 内容                                                 |
| ------------------------------ | ---------------------------------------------------- |
| `designVersion` / `buildRunId` | 评审针对的方案版本与构建                             |
| `objective`                    | 尺寸、房间数、洞口、路线、悬空、预算、禁项等实测     |
| `visual`                       | 看图评审：意图、体量、比例、立面、檐口、细部、室内外 |
| `defects`                      | 分类：设计缺陷 / 施工缺陷 / 偏好变化 / 能力限制      |
| `verdict`                      | 满足 / 部分满足 / 不满足；必须项逐条                 |
| `nextAction`                   | 接受、局部修改、重做方案、向用户提问                 |

## 6. 交互流程

### 6.1 状态机

```text
intake
  → understand（抽取需求、标注来源、找歧义 / 矛盾）
  → clarify（只问高影响问题；可跳过）
  → design（场地 / 功能 / 体量 / 平面 / 结构 / 外观 / 细部）
  → check（确定性检查 + 预览）
  → review（用户看图 / 读摘要）
  → revise（用户改主意或方案有问题）→ design
  → confirm（用户确认方案版本）
  → compile（生成 BuildBrief / BuildSpec / gates / 预览）
  → build（调用现有构建 agent）
  → post-review（结果 vs 方案）
  → accept / targeted-revision / redesign
```

### 6.2 提问策略

- 先判断问题是否改变：用途、主要空间、入口 / 朝向、层数 / 体量、风格 / 材料、预算 / 交付范围。
- 不改变这些的细节，给默认建议并标注 `assumed`，不追问。
- 每个问题给出推荐答案与后果，不让用户做无上下文的填空。
- 用户说“你决定”时，记录授权范围，继续设计；不把授权解释成无限自由。
- 需求矛盾时，先给两个可行取舍及影响，再让用户选；不要同时保留互斥要求。
- 用户改主意时，说明受影响的空间、尺寸、动线、外观与已确认决定，生成新版本；旧版本保留。

### 6.3 示例（茶亭，示意）

**用户**：想在村口做一间小茶室，能看稻田，最好有点日式感觉，预算不要太高。

**Agent（理解 + 提问）**：

> 我理解为：村口独立小体量，主要给路人喝茶 / 短暂停留，视线朝稻田，木、石、纸感为主，不希望做成大房子。两个问题会改变布局：
>
> 1. 是否需要一个小柜台和储物间？我建议有，约 6–8 m²，放在入口侧。
> 2. 稻田在场地哪一侧？我建议把主要开口和檐下平台朝向稻田，入口从道路一侧退进一小段。

**用户**：需要柜台，稻田在南边，想要大一点的屋檐，室内能坐 10 人。

**Agent（方案）**：

> 建议 8×6 m 主体，南侧 1.5 m 深檐下平台，室内 10 个座位沿窗和柜台布置；北侧入口做 1 m 退进的玄关，柜台和储物在西北角。双坡屋顶，檐口压低到 3.2 m，屋脊 5.4 m；木柱 + 石基座 + 深色瓦屋面，室内用浅木和米色墙面。这样从入口先看到柜台，再转向南侧稻田，形成“收—放”的序列。方案 0.1 的平面和轴测图如下。

**用户**：可以，屋檐再深一点，别太像旅游景点。

**Agent（修改 + 影响）**：

> 把南侧檐口从 1.5 m 加到 2.2 m，需要把南侧柱列外移 0.7 m，室内净面积不变；屋脊高度不变。这样檐下平台更像日常停留，而不是售票亭。方案 0.2 已更新，未改动的部分保持不变。

**用户**：确认。

**Agent**：编译构建简报，交给构建 agent；构建完成后按同一方案评审。

这个示例的重点：agent 主动设计、只问关键问题、用图和数字说明、修改时说明影响。

## 7. 建筑专业分析与设计

### 7.1 分析阶段

| 阶段 | 内容                                                            | 产出                |
| ---- | --------------------------------------------------------------- | ------------------- |
| 场地 | 朝向、日照、主导风、排水、入口、退界、周边视线 / 噪声、室外分区 | 场地策略与总平面    |
| 功能 | 空间清单、面积、人数、相邻 / 分离、公共 / 私密 / 服务、储存     | 功能气泡图 / 面积表 |
| 体量 | 体量策略、层数、檐口 / 屋脊、与场地关系、主次                   | 2–3 个体量选项      |
| 平面 | 房间 bounds、墙厚、门窗、交通、家具区、结构柱网                 | 带尺寸平面          |
| 结构 | 墙承重 / 框架、跨度、楼板、悬挑、屋面支撑                       | 结构策略与限制      |
| 围护 | 立面开间、窗墙比、框、腰线、基座、檐口、屋面                    | 立面 / 剖面         |
| 环境 | 采光、通风、遮阳、保温、雨水                                    | 被动策略            |
| 细部 | 门槛、窗台、栏杆、排水、灯具、固定家具                          | 细部表              |
| 室内 | 主要空间序列、视线、家具、材料延续（若在范围）                  | 室内策略            |

### 7.2 确定性检查（建议首版）

| 检查        | 规则示例                                          | 来源                         |
| ----------- | ------------------------------------------------- | ---------------------------- |
| 面积        | 各空间面积与总面积一致；净面积 / 建筑面积比例合理 | `DesignScheme`               |
| 层高 / 净高 | 主要空间净高 ≥ 2.4 m；楼梯 / 走廊头顶 ≥ 2.1–2.4 m | 小建筑规则                   |
| 门洞        | 主入口 ≥ 1.2 m；室内门 ≥ 0.8–0.9 m；门洞不堵路线  | 规则库                       |
| 楼梯        | 踏步高 / 深、连续踏面、平台、净空；连接两层       | 复用 `stairWalkability` 口径 |
| 走廊        | 主要通道 ≥ 1.0–1.2 m；家具不侵占                  | 规则库                       |
| 结构跨度    | 木 / 石 / 混凝土 / 钢的合理跨度区间；悬挑限制     | 规则库（启发式）             |
| 屋面        | 坡度与材料匹配；檐口 / 屋脊连续；排水方向         | 规则库                       |
| 采光        | 主要空间窗地比 / 窗墙比下限；避免无窗房间         | 规则库（启发式）             |
| 路线        | 入口 → 主要空间 → 次要空间；关键站立点可达        | `@pg/design/routes`          |
| 净空        | 门厅、楼梯、家具、结构不侵入关键净空              | `@pg/design/checks`          |
| 预算        | 实心方块估算 ≤ 上限；体量不超范围                 | 估算器                       |
| 禁项        | 不出现第二栋、城市级场景、未授权巨构              | `BuildSpec`                  |
| API         | 所有构件 / 方块 / 尺寸在当前能力内                | 能力卡                       |

这些规则是设计辅助与可核对事实，不等同于建筑规范审查；报告要写明“启发式”与“未校准”。

### 7.3 能力卡

建议从以下来源生成并版本化：

- `packages/geometry/world.d.ts` 与 `schema.ts`：构件、参数、限制、写入层、坐标约定。
- `packages/modeling/src/schema.ts`：ModelDocument 上限与部件角色。
- `packages/analysis`：测量口径与限制（例如 y ≤ 1 作为地面、地下渲染跳过）。
- `packages/render/src/camera.ts`：现有七视角；没有人眼 / 室内视角。
- `packages/agent/src/prompt/system.ts`：当前构建范围（外观 / 可进入 / 不做内饰）。

能力卡要回答：

- 能建什么：墙、板、坡 / 平屋面、楼梯、门窗、柱廊、栏杆、院墙、铺装、参数壳、草模导入。
- 不能建什么：实体物件（盔甲架 / 展示框）、动态电梯、真正地下空间展示、任意室内精细家具的完整支持。
- 边界：坐标范围、方块预算、渲染视角、分析限制、沙箱墙钟。
- 替代方案：不能做时给什么可交付的近似，并在方案中标注。

### 7.4 知识包

建议维护四类、可版本化的 Markdown / JSON：

1. **类型学**：亭 / 廊、院落、L 形、条形体量、错层、屋顶平台、山居、街角。
2. **风格**：现代简约、木石乡野、新中式、工业、温暖极简等；每类给材质明度、开窗、屋面、细部规则。
3. **功能**：住宅、茶室 / 咖啡、工作室、书店 / 图书馆、展厅、驿站；给面积、邻接、净高、采光、家具。
4. **细部做法**：檐口、窗框 / 窗台、门槛、栏杆、屋脊、排水、灯具、长凳、书架、铺装图案；每条写清构件 / 方块与常见错误。

知识包是产品知识，不是会话记忆；更新要有来源与版本，不自动从单次运行“学习”。

## 8. 提示词生成

### 8.1 提示词包

交互层不直接“写一段很长的 prompt”，而是编译出：

```text
BuildBrief
  ├─ design.md            用户确认的方案（唯一依据）
  ├─ build-task.md        构建 agent 看到的四节题面
  ├─ build-spec.json      机器约束
  ├─ gates.json           现有门槛可表达的部分
  ├─ reference/           方案图 / 平面 / 剖面 / 轴测
  └─ prompt-meta.json     版本与能力卡指纹
```

### 8.2 `build-task.md` 模板

为兼容现有 `extractTaskBody`（标题 + 一至四节），建议四节：

1. **需求与设计意图**：用户是谁、建筑做什么、场地故事、一句话概念、优先级。
2. **禁止项与边界**：不能改的布局 / 尺寸 / 主要材质、不能出现的体量 / 场景、能力限制。
3. **场地、尺寸与建造要求**：坐标原点、bounds、标高表、房间表、门窗表、楼梯 / 路线、结构、屋面、立面、材质、细部做法、场地铺装。
4. **验收与自由发挥**：必须项逐条、可核对的自查方法、可自由设计的范围、构建层遇到冲突时的返回方式。

写作规则：

- 坐标、尺寸、数量用表格；同一数字只出现一次，其他位置引用表格。
- 先写“不可改”的，再写“可发挥”的；不要把审美偏好写成机械硬性。
- 每个 must 都能在图上或测量里核对；不能核对的写成偏好。
- 细部做法给公式 / 示例，不只给形容词。
- 明确“若无法实现，返回冲突与建议，不要自行改方案”。
- 控制长度：优先结构化信息，不重复 system prompt 里已有的 API 说明。

### 8.3 编译与检查

```text
DesignScheme
  → 需求覆盖检查（每个 must 有落点）
  → 尺寸 / 面积 / 标高一致性
  → 结构 / 净空 / 路线检查
  → 能力卡检查（构件、方块、渲染、分析）
  → 方块预算估算
  → 生成 BuildBrief / BuildSpec / gates
  → 提示词 lint（长度、重复、禁项、可核对性）
  → 交给构建 agent
```

`brief/lint.ts` 的最小规则：

1. 每个 `must` 需求在 `build-task.md` 或 `BuildSpec` 中有对应条目。
2. 所有尺寸只来自 `DesignScheme` 的规范表，不出现第二套数字。
3. 每个空间有 bounds、面积、层、入口 / 连接。
4. 每个洞口有 host、位置、宽高、窗台 / 过梁。
5. 每个楼梯连接两个面，给出踏步、平台、净空。
6. 每种材料是 `assets` 注册表里的合法方块。
7. 每种做法在当前 World API / 能力卡内；否则转成限制说明。
8. 估算方块数 ≤ 预算；体量在首版范围内。
9. 禁项没有互相矛盾；没有“第二栋 / 城市级 / 巨构”的遗漏。
10. 提示词不超过约定 token 预算；超长时先删重复解释，不删 must。

### 8.4 交给构建层

首版最小接线：

- `tools/design-agent.ts` 组装：交互层 + `runRun` + `check` / `render` / `store`。
- 构建用 `task.fed` = `build-task.md` 正文；`initialDesign` = `design.md`；`initialImages` = reference 图。
- 通过现有 `--gates` 或直接传 `GateConfig` 传入 `gates.json`。
- 构建 system prompt 增加“方案已确认”模式：
  - 不得改变主要布局、房间用途 / 数量、外部尺寸、层高、入口、主要材质、屋顶形式、用户点名细节。
  - 可自由处理构造、局部装饰、铺装图案、灯具与家具细节（若在范围）。
  - 无法实现时停止并报告冲突，不自行改方案。
- 首版不要求交互层生成完整代码骨架；先用“方案 + 坐标表 + 预览图 + 门槛”验证。若构建漂移仍然严重，再加“矩形 / L 形小建筑的离线验证骨架生成器”，作为 Phase 2b。

### 8.5 提示词变体

建议新增：

- `craft-small`：面向小体量的形态 / 细部提示。内容包括：
  - 真实尺度：层高 3.2–4.0 m、门 2.1–2.4 m、窗台 0.8–1.0 m、檐口 0.6–2.0 m、栏杆 0.9–1.1 m。
  - 基座 / 墙身 / 檐口 / 屋脊的明度层次；3–5 档材料，不靠尖塔。
  - 窗框、窗台、门框、门槛、雨棚、栏杆、檐口收边、屋脊、排水、灯具、长凳、书架等做法。
  - 开间节奏、窗墙比、入口序列、檐下空间、室内外连续。
  - 反例：缩小版哥特、满墙尖塔、无收口平顶、超大屋檐压墙、单色盒子。
- `scope` 选项：`exterior` / `exterior+entry` / `exterior+interior`；小建筑默认 `exterior+interior`，包含主要空间、家具、楼层与固定家具；构建提示不再无条件写“不做内饰”。
- 其他变体保持现状；`craft` 仍可用于哥特 / 巨构回归，不作为小体量默认。

## 9. 小体量基准与质量

### 9.1 规模守卫

交互层在 intake 阶段做规模判断：

- 首选：1–3 层、8–30 m 占地、≤ 15 m 高、5k–30k 方块。
- 超出时：先说明成本 / 时间 / 质量风险，建议缩小；用户坚持才进入“大型 / 实验”模式，并单独授权预算。
- 禁止：默认把“小屋”放大成巨构、用体量代替设计、用尖塔 / 装饰堆精致。

### 9.2 首批试点题目（建议 4 个）

| id  | 类型                | 规模                         | 重点                                 | 是否含室内        |
| --- | ------------------- | ---------------------------- | ------------------------------------ | ----------------- |
| S1  | 溪畔茶亭 / 咖啡亭   | 8×6–12×8，1 层 + 檐下平台    | 轻、透、檐口、入口序列、看景         | 是（柜台 + 座位） |
| S2  | 村口木石小屋 / 山居 | 10×8–14×10，1–2 层           | 石基 / 木墙 / 坡屋顶、真实尺度、门槛 | 是（主要起居）    |
| S3  | 街角工作室 / 小书店 | 12×9–16×12，2 层             | 平顶、街角、窗带、入口、材料层次     | 可选（一层）      |
| S4  | 小型院落 / 民宿     | 地块 24×20–32×28，2 栋小体量 | 围合、主次、轴线、院墙 / 铺装        | 可选              |

题目要故意包含：

- 一个模糊点（用途、人数、朝向、风格）。
- 一个矛盾点（想要大窗但又要私密 / 想要大屋檐但场地小）。
- 一个用户偏好（材料、氛围、看景）。
- 一个能力边界（例如想要动态电梯 / 实体家具 / 真地下），测试是否诚实说明。

### 9.3 质量 rubric

建议 0 / 1 / 2 三档，按维度给 profile，不合成单一“审美分”：

| 维度           | 0                    | 1                 | 2                                |
| -------------- | -------------------- | ----------------- | -------------------------------- |
| 意图与场所     | 通用盒子，不回应场地 | 回应入口 / 朝向   | 有明确的场所策略与记忆点         |
| 体量与比例     | 过大 / 过小 / 失衡   | 体量成立          | 小体量比例舒展、主次清楚         |
| 平面与动线     | 房间 / 入口不清或堵  | 功能可用          | 有门槛、序列、视线与高效动线     |
| 结构与建构     | 悬空 / 结构不可读    | 结构成立          | 结构与形式一致、节点可读         |
| 立面节奏与材质 | 单色平墙             | 有分层 / 开间     | 节奏、明度、进退、框景完整       |
| 屋面与檐口     | 无收口 / 压墙        | 完整屋面          | 檐口、屋脊、排水、细部比例好     |
| 人体尺度细部   | 几乎没有             | 有门窗框 / 栏杆等 | 窗台、门槛、长凳、灯具、家具连贯 |
| 室内外连续     | 无室内 / 断开        | 主要空间可用      | 视线、光线、材料、檐下空间连续   |
| 完成度         | 大缺陷               | 小缺陷            | 干净、无穿模 / 悬空 / 断梯       |

“精致”建议门槛：所有 must 满足；无 0 分项；总分 ≥ 12/18；再经 owner 盲评确认。阈值只作为初版，校准后再定。

### 9.4 基准调整

- 新增 `benchmark/small/`（或 `assets/v02/benchmark/tasks/small/`）作为开发主线；6–8 题，1–3 层、5k–30k 方块。
- 现有 f1 / f2 / f3 / f6-small 保留为小体量回归；f4 / f5 与大型题降为 `legacy/regression`，不作为日常优化目标。
- 每个题面分两层：
  - `user-brief.md`：给交互层的原始需求（可模糊、可矛盾）。
  - `design-gold.md`：人工确认的方案 / 验收点，用于评交互层，不喂给构建层。
- 构建评估仍用确认后的 `build-task.md`，不能用原始模糊 brief 直接评构建层，否则不公平。
- 机械判据优先：尺寸、房间数、洞口、路线、悬空、预算；审美用盲评 rubric。

### 9.5 验证实验

| 实验          | 对比                                      | 观察                                     |
| ------------- | ----------------------------------------- | ---------------------------------------- |
| E0 交互离线   | 6 个 brief：模糊 / 矛盾 / 详细 / 授权自由 | 需求覆盖、提问质量、方案一致性、能力诚实 |
| E1 提示词质量 | 生成 brief vs 基线题面 / 人工执行版       | 构建条款满足、轮数、成本、盲评           |
| E2 端到端     | 直接构建 vs 交互确认后构建                | 交付率、主要布局偏离、owner 10 分钟接受  |
| E3 定向修改   | 一次“只改点名部分”的反馈                  | 修改成功率、未点名区域变化、成本         |
| E4 小体量基准 | 新 S 题 vs 旧 f 题                        | 质量、成本、方差、失败类型               |

小样本只报告观察，不做显著性结论；真实运行逐批授权。

## 10. 路线图

### Phase 0：定方向与脚手架（约 1–2 个工作日）

产物：

- 本文档 + 首批 4 个试点 brief。
- `@pg/interaction` 包骨架、层级登记、tsconfig / 依赖 / 测试配对。
- `RequirementGraph` / `DesignScheme` / `BuildBrief` / `ReviewReport` 的 zod schema。
- 能力卡生成脚本（从 `world.d.ts` / `schema.ts` / `camera.ts` / 分析口径）。
- 不调用真实模型。

退出条件：`npm run check` 通过；schema 有单测；能力卡能列出“能 / 不能 / 限制”。

### Phase 1：交互与方案（约 3–5 个工作日）

产物：

- 会话状态机、session store、预算 / 取消。
- 需求抽取、歧义 / 矛盾检测、提问策略。
- 设计分析、`DesignScheme` 生成、确定性检查。
- 方案摘要 + 平面 / 剖面 / 轴测预览（先 CLI / 静态 HTML，不依赖完整 Web）。
- 6 个 mock 场景：模糊、矛盾、详细、授权自由、能力不足、用户改主意。

退出条件：离线方案能覆盖 must、维度一致、无静默能力承诺；owner 评审 2 个方案认为“看得懂、可讨论”。

### Phase 2：提示词与构建交接（约 3–4 个工作日）

产物：

- `BuildBrief` 编译器、linter、`BuildSpec`、`gates.json`。
- `tools/design-agent.ts` 接现有 `runRun`；固定方案模式。
- mock 端到端（设计 → 简报 → 构建 → 交付）。
- 如需要，矩形 / L 形小建筑的离线验证骨架生成器（Phase 2b，可选）。
- 2 次小体量真实运行（owner 单独授权）。

退出条件：构建结果不偏离主要布局；构建失败能返回具体冲突；单次成本在预算内。

### Phase 3：结果评审与定向修改（约 2–3 个工作日）

产物：

- 结果 vs `BuildSpec` 客观对比。
- 看图评审与缺陷分类（设计 / 施工 / 偏好 / 能力）。
- 定向修改：新 run + 旧稿 + 明确反馈；未点名区域变化检查。
- 入口 / 人眼 / 室内 / 细部渲染视角（可放 Phase 3 后半）。

退出条件：一次“只改点名部分”的反馈能正确执行；未点名区域无重大变化；用户能看懂评审报告。

### Phase 4：基准、校准与 Web（约 3–5 个工作日）

产物：

- 小体量基准 6–8 题 + rubric 校准。
- E0–E4 小样本实验与结论。
- Web：对话 + 方案板 + 3D 查看 + 确认构建 + 结果 / 评审。
- 巨构题降为回归，小体量成为默认演示。

退出条件：owner 在 10 分钟内能完成一次“需求 → 方案 → 构建 → 看图 → 一次修改”的完整体验。

## 11. 风险与待确认

| 风险                | 说明                                                          | 缓解                                                                       |
| ------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 模型设计能力        | 单模型 deepseek-flash 可能给出通用 / 平庸方案                 | 结构化知识包、分阶段提示、确定性检查、owner 校准；必要时再讨论更强模型     |
| 过度提问            | 交互变成问答疲劳                                              | 影响优先、默认建议、每轮 ≤ 3 问、简单需求零提问                            |
| 方案与施工漂移      | 构建 agent 自行改布局                                         | 固定方案模式、`initialDesign`、`BuildSpec` / gates、结果对比               |
| 提示词过长          | 设计信息多，token 成本上升                                    | 表格化、去重、只给构建必要信息、lint 长度                                  |
| 设计不可实现        | 交互层承诺当前 API 做不到的东西                               | 能力卡、brief lint、构建前冲突返回                                         |
| 审美主观            | rubric 可能机械化或过拟合                                     | 盲评、双判、owner 校准、profile 而非单一分数                               |
| 现有 Blueprint 不足 | 只有粗体量 / 净空 / 路线，缺洞口与细部                        | 交互层自有 `DesignScheme`；Blueprint 只作预览快照；按需扩展                |
| 室内保真度          | 当前方块 / 渲染器对门、活板门、地毯、家具、原木六面等支持不足 | A 线先补专用画法 / 朝向 / 顶侧面区分；设计报告只使用已支持或明确近似的方块 |
| 真实运行成本        | 交互 + 构建多次调用                                           | 会话预算、离线 mock、逐批授权、先小体量                                    |

需要 owner 确认的决策：

1. **首批试点**：茶亭、村居、街角工作室、小院，是否按这四个先做？
2. **入口形态**：首版 CLI（推荐）还是直接 Web？
3. **构建交接**：首版只交“方案 + 简报 + 图”，还是同时要求生成可执行的代码骨架？
4. **旧基准定位**：f4 教堂 / f5 塔楼是否降为回归，不再作为日常优化目标？
5. **模型策略**：交互层是否先只用 deepseek-flash；若设计质量不足，是否允许单独评估更强模型（不自动切换）？
